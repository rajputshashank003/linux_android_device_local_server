# MyFile Hosting Platform (Termux)

## Current support level

The runtime is Termux PRoot-Distro 5.3.0, which can pull and unpack OCI/Docker registry images and run an image's configured entrypoint without a Docker daemon or root. On this device, an ARM64 `nginx:alpine` image was pulled and run through the deployment controller; it served HTTP 200 locally, was reverse-proxied through MyFile, stopped, restarted, and deleted. A three-process Node source integration test also verified concurrent distinct ports and independent lifecycle actions.

This verifies only that image and configuration on this device. It does not establish broad Docker compatibility or Android 10 compatibility. The detected device is a Samsung SM-X115 running Android 16, ARM64, under non-root Termux.

## Install and diagnose

From Termux, install the small runtime package if absent:

```sh
pkg install proot-distro
python -m execution_engine.diagnostics
python -m execution_engine.oci_smoke
```

`oci_smoke` never downloads an image. It runs only the fixed `myfile-phase1-nginx` alias when that test image has already been installed. The report's OCI result is `NOT VERIFIED` if the fixed image is absent.

The control panel is available in MyFile's **Host** tab after the updated application code is running. Management APIs use the existing MyFile Basic authentication:

- `GET /api/hosting/status`
- `GET /api/hosting/apps`
- `GET /api/hosting/apps/<id>`
- `GET /api/hosting/apps/<id>/logs`
- `POST /api/hosting/apps` (queue image preparation and start)
- `POST /api/hosting/apps/<id>` with actions `start`, `stop`, `restart`, `redeploy`, `publish`, `delete`

Deleting requires `{"action":"delete","confirm":"<same-app-id>"}`. All identifiers are generated by the server; no API accepts a shell command string or filesystem path. An optional command is a JSON argv array. App environment values and command arguments are stored in mode-0600 files under the private MyForever data directory; the API does not return them. They are not encrypted, so protect the Termux account and device lock. Secrets are redacted from the app log stream.

## Runtime behavior and limits

- Multiple deployments may prepare/run concurrently, bounded by available memory, CPU, storage, ports, and the runtime. Host ports 20000–29999 are uniquely allocated and persisted per deployment; port 8000 and the runtime metrics service on 20241 are reserved. Ports are checked against the OS and existing records. Resource status provides advisory low-memory/storage warnings; it does not enforce limits. Image installation operations are serialized to avoid concurrent large pulls. The default image preparation preflight requires 2 GiB free in the PRoot-Distro filesystem and rejects an unpacked rootfs above 1.5 GiB. PRoot-Distro also maintains a shared image-layer cache; its cache is not automatically removed when one app is deleted.
- Host ports are assigned uniquely per deployment and conflict checks include OS listeners and persisted records. Node source applications use a preload adapter to remap common `net.Server.listen()` calls to their assigned loopback port; PRoot does not offer Docker port mappings: the tested standard Nginx config is adapted to a distinct loopback host port, while other images must honor the injected `PORT` value or otherwise be specifically compatible. PRoot `--redirect-ports` only shifts privileged ports by its fixed offset; it is not general port forwarding. OCI application ports may bind host interfaces and can be reachable from the LAN.
- App status becomes `running` only after an HTTP GET to the configured health path returns 2xx or 3xx. Process status is checked from the manager's process handle or the verified `/proc` PID/start-time/command identity after a control-plane restart.
- Pull progress is available in bounded, private per-app logs; the server is not blocked while the image is downloaded. Image pulls are serialized and time out after 15 minutes. There is no layer-size limit in PRoot-Distro itself; the preflight and post-unpack size check cannot prevent a registry download from temporarily consuming more space than expected.
- App logs are capped with one rotated file; the separate log-writer process lets a running app continue logging if the MyFile control plane restarts. Environment values and command secrets are redacted.
- Private registry authentication is not implemented. Do not place credentials in image references.
- PRoot emulates filesystem operations in userspace; it is not a kernel container or a safe boundary for untrusted code. It shares Android's kernel and network namespace, has no cgroup resource controls, and application ports may bind host interfaces and be reachable by LAN clients directly. The platform is for trusted, administrator-controlled applications only, not arbitrary public multi-tenant code.
- Publishing explicitly bypasses MyFile's Basic password for that app path. The app port may also be reachable directly on the LAN. The UI requires confirmation. Unpublished app routes still require MyFile authentication.
- The reverse proxy supports ordinary HTTP methods, bounded request bodies, and HTTP responses; WebSocket upgrade is not implemented. Applications must tolerate running below `/hosted/<id>/` or serve paths relative to that prefix. Absolute-root assets, redirects, and frameworks that require a root hostname may need app-specific base-path configuration.
- The stable local route is `http(s)://<existing-origin>/hosted/<id>/`. Existing port 8000, Cloudflare Tunnel, DNS, and server authentication configuration were not changed. Public routing through the current tunnel and HTTPS were not tested externally; this URL is not claimed to be publicly reachable.
- The process manager does not promise recovery after Android kills Termux or after a device reboot. The existing Termux supervisor is untouched. Device sleep, battery restrictions, and storage availability remain relevant.

## Integration notes

The deployment layer is `hosting.py` plus a small detached log collector (`hosting_log_writer.py`). It uses PRoot-Distro's actual image manifest/config and existing SQLite migration conventions (`app_db.py`, schema version 3). Routes live in `server.py`; the Host interface is part of the existing `ui.html`. No separate deployment daemon, cloud compute provider, Docker socket, or public shell endpoint is introduced.

The runtime's base diagnostics and OCI smoke test are independent of app deployments. A test failure or unavailable runtime does not prevent the ordinary MyFile server from starting; runtime checks happen only when its API is used.

## Phase 2 remaining work

The Nginx end-to-end acceptance path is verified, but other images, routes requiring root-level assets, subdomain routing, WebSockets, resource enforcement, private registries, and untrusted-image isolation are not supported or verified. Stable subdomain hostnames would require an explicitly configured wildcard DNS/tunnel origin route; this project deliberately did not change that infrastructure.


## Generic OCI image compatibility review — 2026-10-20

The Host form accepts ordinary OCI/Docker references, but this is not a claim that every Docker image works. Preparation uses the installed PRoot-Distro 5.3.0 registry pull and manifest/config extraction path and explicitly requests the device-native `aarch64` architecture. The controller inspects `architecture`, `Entrypoint`, `Cmd`, `Env` (only variable names are returned), `WorkingDir`, `ExposedPorts`, `Healthcheck`, and `Volumes`. If no application port is supplied, exactly one declared TCP `EXPOSE` is selected; zero or multiple TCP ports require an explicit HTTP port. Readiness is verified by an HTTP request to that port. A metadata `EXPOSE` declaration is not proof that an application listens there.

| Backend / image class | Current device result |
| --- | --- |
| Native ARM64 OCI image pull + configured entrypoint | PRoot-Distro is installed; `nginx:alpine` was actually executed and its HTTP response verified on this tablet. |
| Native ARM64 HTTP image that honors the injected `PORT` or is otherwise compatible | Potentially supported; must be deployed and health-checked per image. Not universal. |
| Standard ARM64 Nginx on multiple distinct app ports | Nginx listener config adapter is implemented and covered by unit tests; a fresh multi-Nginx live run was not part of this review. |
| AMD64-only image | Unsupported locally in this configuration: no QEMU user-mode emulator is installed or wired into the controller; wrong-architecture images fail before launch. |
| Redis/PostgreSQL or other non-HTTP service | Image may execute, but the public proxy and readiness checks are HTTP-only; not supported as a usable published service here. |
| Docker volumes, arbitrary host mounts, Docker networks, HEALTHCHECK, privileged mode | Not implemented; persistent-volume semantics, healthcheck execution, or Docker isolation are not claimed. |
| Docker Engine / rootless Docker | Unavailable on this non-root Termux environment: Docker CLI/daemon/runtime binaries, user namespaces, delegated cgroups, and rootless helpers are absent or unusable. |
| Remote Docker Engine | Not configured. No remote host or credentials were introduced. |

PRoot shares the host kernel and network namespace; `--isolated` is about filesystem bindings, not kernel/network isolation. It does not enforce CPU or RAM limits. An app process may bind host interfaces directly, so only trusted administrator-managed images belong on this tablet. No image gets Docker-equivalent isolation. The current tablet reports Android 16, ARM64; Android 10 behavior is not verified. Three concurrent app processes were tested through the separate Termux Node.js source workflow, but arbitrary OCI image concurrency is bounded by actual device resources and app port behavior.
